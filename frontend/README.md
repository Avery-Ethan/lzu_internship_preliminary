## 3. 十分钟跑起来

```bash
node -v        # >= 18
npm config set registry https://registry.npmmirror.com   # 装依赖卡住就换源

npm create vite@latest . -- --template vue     # 或 --template react
npm install && npm run dev                      # http://localhost:5173
```

另开一个终端跑数据服务（**零依赖，不用装任何包**）：

```bash
node frontend/mock/server.mjs
# 打开 http://127.0.0.1:3001/api/products 能看到 JSON 就成功了
```

技术栈：**Vue 3 + Vite / React 18 + Vite / 原生 HTML+JS**，三选一，JavaScript 即可。
选原生的不扣分，在 `DESIGN.md` 第 3 节说明选择理由即可。

**环境卡住了怎么办（按顺序试）：**

| 现象 | 处理 |
|---|---|
| `npm install` 卡住 / 超时 | 换源：`npm config set registry https://registry.npmmirror.com`，或 `pnpm install` |
| `node: command not found` | 装 Node 18+（官网 LTS 包，不要用系统自带的旧版） |
| 3001 端口被占 | `PORT=4000 node frontend/mock/server.mjs`，前端请求地址跟着改 |
| 跨域报错 `blocked by CORS` | mock 已开 `Access-Control-Allow-Origin: *`。报错说明请求地址写错了（别写 `localhost:3001` 打错成 `localhost:3000`） |
| `Cannot find module` | 删掉 `node_modules` 和 `package-lock.json`，重新 `npm install` |
| 页面一片空白 | F12 看 Console 第一行红字，**先看报错原文再改代码** |

## 4. 数据与接口约定

### 4.1 字段表

**商品 Product**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | number | 商品 ID |
| `title` | string | 1~50 字 |
| `price` | number | **单位：分**。整数，如 `1250` 表示 ¥12.50 |
| `stock` | number | 库存，0~999 整数 |
| `category` | string | `数码` / `图书` / `服饰` / `食品` / `文具` |
| `status` | string | `on` 在售 / `off` 已下架 |
| `sellerName` | string | 卖家名 |
| `description` | string | 描述，≤200 字 |

**订单 Order**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `orderNo` | number / string | 订单 ID / 订单号（如 `SO202611190001`） |
| `productId` / `productTitle` | number / string | 下单时的商品快照 |
| `quantity` | number | 数量，正整数 |
| `unitPrice` | number | 下单时的单价（分） |
| `totalAmount` | number | **服务端算的**总额（分）= `unitPrice × quantity` |
| `status` | string | `created` 待支付 / `paid` 已支付 |
| `createdAt` / `paidAt` | string / null | ISO 时间 |

**支付 Payment**：`paymentId` / `orderId` / `amount`（分）/ `method`（`alipay`\|`wechat`）/ `status`（`processing`\|`paid`）/ `paidAt`

统一响应包：`{ "code": 0, "message": "ok", "data": ... }`，出错时 `code != 0` 且 `data = null`。

### 4.2 金额口径（全场唯一规则）

- **接口里的钱永远是「分」，整数。** 前端展示时才转成元。
- 界面上一律 `¥xx.xx`，**两位小数，带 ¥**（如 `¥12.50`、`¥0.01`）。
- 用户输入用**元**，提交前转成**分**（元 × 100）。

### 4.3 错误码表

| HTTP | code | message | 什么时候返回 |
|---|---|---|---|
| 400 | 40001 | 各字段的具体提示 | 参数校验失败（价格非正整数、库存越界、标题超长、分类非法、数量非正整数、支付方式非法） |
| 400 | 40002 | 请求体必须是合法 JSON | body 不是 JSON |
| 404 | 40400 | 接口不存在 | 路径写错（**最常见：少写 /api 前缀**） |
| 404 | 40401 | 商品/订单/支付单不存在 | ID 不存在 |
| 409 | 40901 | 库存不足 | `stock < quantity` |
| 409 | 40902 | 商品已下架 | `status = off` 时下单 |
| 409 | 40903 | 订单已支付，请勿重复支付 | 对已支付订单再发起支付 |
| 503 | 50300 | 服务暂时不可用 | 只在开了故障注入时出现 |

> **业务错误必须显示 `message` 给用户**，不能只在 Console 打一行。

### 4.4 排序与分页

- 商品列表**按 `id` 升序**返回；新发布的商品排在**最后**。
- `page` 默认 1，`pageSize` 默认 8，上限 50。
- 你的列表必须能访问到**全部商品**，不能只显示默认的第一页：
  - 做分页 / 「加载更多」，**或**
  - 把 `pageSize` 传大一点一次取全。

### 4.5 故障注入与重置

```bash
ERROR_RATE=1 node frontend/mock/server.mjs     # 所有业务接口 100% 返回 503
ERROR_RATE=0.3 node frontend/mock/server.mjs   # 30% 概率失败，更接近真实网络
```

```bash
curl -X POST http://127.0.0.1:3001/api/_reset  # 数据恢复初始状态
```

> 重启进程也会恢复。改了数据试坏了，用上面任一种方式重置，不用改代码。

## 5. L0 基础（40 分，必做）

> **评审怎么验**：先 `curl -X POST http://127.0.0.1:3001/api/_reset` 把数据恢复成初始状态，再按你 `SUBMISSION.md` 里的命令把项目跑起来，打开首页，然后按下面「验收标准」逐条点。
> 每条 8 分，全部做到 = 40 分。

### L0-1 商品列表（8 分）

**要求**：调 `GET /api/products` 渲染列表。每条至少显示 **标题、价格（`¥xx.xx`）、库存、分类、状态徽标（在售 / 已下架）**。库存为 0 的商品要有明显区分。**数据必须来自接口，不能写死在代码里。**

**验收标准**（评审逐条点）：

- [ ] F12 → Network 里有 `GET /api/products` 且返回 200（证明是接口数据，不是硬编码的数组）
- [ ] 列表中**每一条**价格都是 `¥xx.xx` 两位小数格式、带 `¥`（不出现裸分数值，不省略末尾的 0）
- [ ] 库存为 0 的商品与其它行有**肉眼可见的差异**（灰化 / “缺货” / 按钮禁用，任一即可）
- [ ] **在售** 与 **已下架** 两种徽标都能出现，且与数据一致
- [ ] 标题较长的商品不撑破布局、不换行错位
- [ ] 刷新两次，价格不出现 `NaN` / `undefined` / 未换算的整数分值

---

### L0-2 发布商品表单（8 分）

**要求**：字段为 **标题、价格（用元输入）、库存、分类（下拉）、描述**。提交前把元转成分，调 `POST /api/products`。

**验收标准**：

- [ ] 价格以**元**输入，Network 请求体里 `price` 是**整数分**（元 × 100，如 `19.9` → `1990`）
- [ ] 评审现场抽不同量级的元值输入，`price` 全部正确、全部是整数
- [ ] 分类下拉恰好 5 项：数码 / 图书 / 服饰 / 食品 / 文具
- [ ] 提交后返回 **201**，Console 没有红色报错
- [ ] 表单能提交成功（不是“按钮点了没反应”）

---

### L0-3 发布成功后的反馈（8 分）

**要求**：提交成功 → 有提示 + 表单重置 + 列表里出现这条新商品。

**验收标准**：

- [ ] 成功后有明确提示（toast / alert / 行内成功消息，任一均可）
- [ ] 5 个输入框被清空或回到默认值
- [ ] 列表里**能找到**刚发布的商品（重新请求或前端插入都算；**翻到最后一页也算**）
- [ ] 发布的商品状态是「在售」，价格与输入一致（输入 `12.50` → 列表显示 `¥12.50`）

---

### L0-4 上下架（8 分）

**要求**：每行有「上架 / 下架」按钮，调 `PATCH /api/products/{id}/status`。

**验收标准**：

- [ ] 在售商品的按钮文案是**「下架」**，已下架商品的按钮文案是**「上架」**（文案与状态对得上）
- [ ] 点击后 Network 里出现 `PATCH /api/products/{id}/status`，请求体是 `{"status":"off"}`（或 `on`）
- [ ] 成功后**状态徽标同步变成"已下架"**，按钮文案变成"上架"
- [ ] 对已下架商品点"上架"，徽标变回"在售"
- [ ] 点错按钮 / 快速连点，页面不崩、不出现两条相反状态

---

### L0-5 加载态与空态（8 分）

**要求**：请求进行中有加载提示；筛选无结果时显示空态。

**验收标准**：

- [ ] 首次进页面，数据回来之前有**加载提示**（骨架屏 / "加载中…" / spinner，任一均可）
  - 技巧：F12 → Network → 选 `Slow 3G`，加载态会停留得更久，好观察
- [ ] 搜索一个不存在的关键词（如 `zzz`）→ 显示**"没找到"类提示** + **"清空筛选"按钮**
- [ ] 点“清空筛选”→ 关键词清空，列表恢复为初始状态
- [ ] 空态时**不显示**“加载中”，加载时**不显示**“暂无数据”（两者不能同时出现）
- [ ] 空态不是一片纯白（用户能看出“是没结果”，不是“页面挂了”）

## 6. L1 进阶（15 分）

### L1-6 下单（5 分）

**要求**：列表或详情里点「购买」→ 选数量（正整数）→ 调 `POST /api/orders` → 成功则库存减少，失败要把后端 `message` 显示给用户。

**验收标准**：

- [ ] 有购买入口，能选择数量，`quantity` 提交的是**数字**（不是 `"2"` 字符串）
- [ ] 下单成功后，列表里该商品库存**减少**到正确值
- [ ] 购买数量超过库存时 → 显示后端返回的 **“库存不足”**，页面不白屏
- [ ] 对已下架商品下单 → 显示后端返回的 **“商品已下架”**
- [ ] 所有失败都有**页面上的提示**（不是只打 Console）
- [ ] 下单失败后按钮恢复可点（不会永久禁用）

---

### L1-7 订单列表（3 分）

**要求**：调 `GET /api/orders` 展示订单号、商品名、数量、金额、状态。

**验收标准**：

- [ ] 订单号、商品名、数量、金额、状态五项都能显示出来
- [ ] 状态显示中文 **“已支付” / “待支付”**（不是 `paid` / `created` 原文）
- [ ] 金额是 `¥xx.xx` 两位小数
- [ ] 刚下单成功的订单出现在列表里

---

### L1-8 金额处理（5 分）

**要求**：

- 所有金额只以 `¥xx.xx` 出现，两位小数。
- 元 ↔ 分换算必须准确，**任佥合法的元值换算后都必须是正确的整数分**。
- 下单前的前端预估总价（单价 × 数量）必须等于服务端返回的 `totalAmount`。

**验收标准**（评审现场抽值）：

- [ ] 列表里**所有**价格都是 `¥xx.xx` 两位小数，不出现浮点尾巴（如 `xx.99000001`）、不出现四舍五入偏差
- [ ] 评审从价格输入框输入**几个不同量级的元值**（整数元、一位小数、两位小数、极小金额），请求体 `price` 全部正确且是整数
- [ ] 任选一个商品买多件 → 前端预估显示的金额与服务端返回的 `totalAmount` **完全一致**
- [ ] 页面上不出现 `NaN` / `undefined` / 未换算的整数分值

---

### L1-9 表单校验（2 分）

**要求**：校验不通过时**不发请求**，错误提示显示在对应字段下方。

**验收标准**：

- [ ] 价格：必填、必须 > 0、最多两位小数（输入 `19.999` 被拦下）
- [ ] 库存：必填、0~999 整数（输入 `-1` / `1000` / `1.5` 都被拦下）
- [ ] 标题：1~50 字（空标题、51 字都被拦下）
- [ ] 校验失败时 **Network 里没有 `POST /api/products`**（这是重点：前端拦住，不是靠后端报错）
- [ ] 错误提示显示在**对应字段下方**（不是所有错误弹一个 alert）

## 7. L2 挑战（10 分，任选 1~2 个）

> ### L2-10 支付链路（6 分，推荐）

**要求**：订单列表「去支付」→ 选支付方式 → `POST /api/payments` → 按钮"支付中…"并禁用 → **轮询** `GET /api/payments/{paymentId}` → `paid` 后更新状态并永久禁用。

**验收标准**：

- [ ] 待支付订单有「去支付」，能选支付宝 / 微信
- [ ] 点支付后按钮变成 **"支付中…"** 且 `disabled`（不能连点）
- [ ] Network 里能看到**多次** `GET /api/payments/{paymentId}`，间隔约 **1 秒**
- [ ] **轮询返回 `processing` 时，界面必须保持“支付中”，不能提前报成功**
- [ ] 变成 `paid` 后：提示成功 + 订单状态变成"已支付" + 按钮**永久禁用**
- [ ] 轮询有**上限**（最多 10 次左右），到上限后停止并提示"支付状态未确认，请稍后在订单列表查看"
- [ ] **离开页面停止轮询**：点支付后立刻切到别的页面（或关闭该组件），5 秒内 Network 里**不再有新的** `GET /api/payments` 请求
- [ ] 对**已支付**的订单点支付 → 正确显示后端返回的 **“订单已支付，请勿重复支付”**

> ---

### L2-11 防重复提交（6 分）

**要求**：下单按钮点击后禁用并显示"提交中…"，连点只产生 1 个订单。

**验收标准**：

- [ ] 点击后按钮立即 `disabled` + 文案变"提交中…"
- [ ] 快速连点 5 次，Network 里 `POST /api/orders` **只有 1 次**
- [ ] 请求返回后按钮恢复可用（**失败了也要能重试**）
- [ ] 用户看到的是“提交中”，不是“按钮消失了”

### L2-12 一个测试（6 分）

**验收标准**：

- [ ] 至少有 2 条 `it/test` 用例，且有断言（`expect(...).toBe(...)`）
- [ ] 用例覆盖**不同量级的元值**（整数元、一位小数、两位小数、极小金额各至少一个）
- [ ] 测试是**真跑过**的（`SUBMISSION.md` 里贴了输出）

---

### L2-13 响应式 / 路由（6 分，二选一）

**A. 响应式**：375px 宽度（iPhone SE）下**无横向滚动**。

- [ ] DevTools 切到 375px，页面不出现横向滚动条
- [ ] 商品卡片、表格、表单都能完整看到（不是被裁掉一半）
- [ ] 文字不被截断成这样：`降噪蓝牙耳…`（可以截断但要能看出是省略，不是堆叠）

**B. 路由**：做 `/products/:id` 详情页。

- [ ] 从列表点进详情，URL 变成 `/products/3`，显示该商品完整信息
- [ ] 详情页有「返回」，能回到列表
- [ ] **直接在新标签页打开** `http://localhost:5173/products/1` 能正常显示（不是白屏）
- [ ] 不存在的 id（如 `/products/9999`）有"商品不存在"提示，不是白屏

## 8. 明确不做

这些**不在本轮考察范围**：

| 不做 | 原因 |
|---|---|
| 登录 / 注册 / 权限 | 放在 L2 之外单独考，这轮不测 |
| 图片上传 / 富文本编辑器 | 和本轮要测的能力无关 |
| 自己写后端 / 自己写数据库 | mock 就是接口 |
| 修改 `mock/` 下的任何文件 | 评审用原始 mock，你的改动不生效 |
| 整套后台模板（vue-element-admin、Ant Design Pro 等） | 会掩盖你自己的判断。组件库可以用，整站模板不行 |
| 小程序 / 移动端 App | 不是同一套技术栈 |

**判分原则（对每个人都一样）：**

2. **样式丑不扣分。** 只扣"接口格式读错""数据没渲染出来"这类。
3. **接口字段读错**（把 `data.items` 当 `data`、把 `price` 当元）→ 对应条不给分，但其它条照常给。
4. **项目跑不起来**：如果是环境/依赖问题且 `SUBMISSION.md` 写清了，按代码里的实现给**一半分**；如果什么都跑不了又没有说明，按 0 分算（红线）。
5. **能跑但点不动**（按钮无响应、报错白屏）→ 该条不给分。这条最伤分，交之前自己把每条点一遍。

## 11. AI 使用怎么拿这 20 分（重点）

| 维度 | 分值 | 3 分水平 | 满分水平 |
|---|---|---|---|
| **模型选型** | 6 | 全程同一个模型 | 简单任务用 flash 级，卡住/设计类问题换强模型，**能说出为什么换** |
| **提问与上下文** | 5 | 一次把整个项目贴进去 | 问题切小、给足上下文但不过量；同一问题不反复问 5 次 |
| **是否用 AI 验证** | 5 | 只让它"帮我写" | 让它 review、解释报错、检查边界；**会拿自己的判断否掉它的建议** |
| **成本意识** | 4 | 40 元花完、代码没跑通 | 花得少、产出高；能说清哪类问题不值得问 AI |

**三个具体信号（我们有平台日志，会和 `AI_USAGE.md` 对账）：**

- 改个 CSS、写个正则用最贵的模型 → 扣分
- 单次输入几万 token（把整份题目 / 整个 `node_modules` 塞进去）→ 扣分
- 出现"帮我 review 这段""这个边界对吗""这个报错是什么意思"这类请求 → **加分**

**正例（写进 `AI_USAGE.md` 的合格样子）：**

> 订单列表要显示状态。我先让它解释后端返回的 `created` / `paid` 语义，再让它 review 我写的状态映射，它指出我没处理未知枚举值，我补了兜底文案。后来我让它检查轮询的清理逻辑，它列出了三处没清理的地方，我按自己的判断只改了两处（第三处是我故意的）。

**反例：**

> 用 AI 生成了一个电商系统，功能都能跑。

> 四个子项里，**"是否用 AI 验证"最容易拿分也最容易被忽略**——你只要在卡住的时候多问一句"这段有什么边界问题"，就有东西可写。
